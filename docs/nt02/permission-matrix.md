## Part 1: English Section

### 1.1 Declarative Route Policy Architecture (`RoutePolicyRegistry` & `SecurityConfig`)

Rikkei Jobs enforces **deny-by-default** authorization across all HTTP endpoints using one single declarative source of truth: `com.rikkei.jobs.common.security.RoutePolicyRegistry`.

1. **Single Source of Truth (`RoutePolicy` + `PolicyAccessType`)**:
   - Every mapped endpoint in the application is registered once in `RoutePolicyRegistry.POLICIES` as an immutable `RoutePolicy(method, pattern, accessType, allowedRoles, devOnly, methodScoped, infra, description)` record.
   - `PolicyAccessType` defines three explicit access levels:
     - `PUBLIC`: open without authentication (subject to `devOnly` profile gating).
     - `AUTHENTICATED_ANY`: open to all 5 authenticated roles (`CANDIDATE`, `HR`, `MENTOR`, `STAFF`, `ADMIN`).
     - `ROLES`: restricted to an explicit non-empty subset of the 5 canonical roles.
   - `SecurityConfig.securityFilterChain(HttpSecurity)` iterates over `RoutePolicyRegistry.policies()` in exact list order, skips `devOnly` entries when the `dev` Spring profile is inactive, and terminates with `.anyRequest().denyAll()`. Any unmapped or unmatched path returns `401 UNAUTHORIZED` for anonymous callers (`CustomAuthenticationEntryPoint`) and `403 FORBIDDEN` for authenticated callers (`CustomAccessDeniedHandler`).
2. **Literal-Before-Parameterized Ordering Invariant**:
   - Specific literal paths MUST appear before parameterized sibling paths in `RoutePolicyRegistry.POLICIES` so Spring Security's first-match `RequestMatcher` evaluation never shadows a stricter `/me` policy:
     - `/api/v1/profiles/me/skills` and `/api/v1/profiles/me/skills/recompute` (`CANDIDATE` only) appear before `/api/v1/profiles/{userId}/skills` (`CANDIDATE`, `HR`).
     - `/api/v1/companies/me` (`GET`, `PUT`) and `/api/v1/companies/me/logo` (`HR` only) appear before `/api/v1/companies/{id}` (`HR`, `STAFF`).
   - `RoutePolicyRegistryTest` asserts this ordering invariant directly.
3. **Method Scoping & HTTP `405 METHOD_NOT_ALLOWED` Preservation**:
   - Single-policy paths where unsupported HTTP methods must reach `DispatcherServlet` and produce unified `405 METHOD_NOT_ALLOWED` (instead of `403`/`401` on the wrong method for authorized roles) set `methodScoped = false` (`/api/v1/auth/forgot-password`, `/api/v1/health`, `/api/v1/companies/me/logo`, `/api/v1/companies/{id}`).
   - Notably, for `/api/v1/companies/{id}` (`D6` + Team Lead follow-up decision), `methodScoped = false` with `ROLES(HR, STAFF)` ensures:
     - Anonymous `PUT /api/v1/companies/{id}` -> `401 UNAUTHORIZED`.
     - `CANDIDATE`, `MENTOR`, `ADMIN` `PUT /api/v1/companies/{id}` -> `403 FORBIDDEN`.
     - `HR` or `STAFF` `PUT /api/v1/companies/{id}` -> reaches `DispatcherServlet` and returns `405 METHOD_NOT_ALLOWED` identically across own company, cross-company (`2`), and nonexistent ID (`999999`) with zero DB mutation (replacing DN-01's pre-NT02 `404` behavior when `/{id}` had no route).
4. **Filter Chain Precedence (`MustChangePasswordFilter` vs `@PreAuthorize`)**:
   - Request execution order: `JwtAuthFilter` -> `MustChangePasswordFilter` -> Spring Security `AuthorizationFilter` (`RoutePolicyRegistry`) -> `@EnableMethodSecurity` (`@PreAuthorize`) -> Service `OwnershipGuard`.
   - Accounts with `must_change_password = true` (such as seeded `hr1@rikkeijobs.test`) receive `403 MUST_CHANGE_PASSWORD` on every non-allow-listed endpoint before role or ownership checks execute. `MustChangePasswordFilter.ALLOW_LIST` permits only auth recovery/profile (`/api/v1/auth/change-password`, `/api/v1/auth/me`, `/api/v1/auth/login`, `/api/v1/auth/sso`, `/api/v1/auth/forgot-password`, `/api/v1/auth/reset-password`), health (`/api/v1/health`, `/actuator/health`), OpenAPI/Swagger paths, `/error`, and `/api/v1/test/**`.
5. **Automated Coverage & `@PreAuthorize` Parity**:
   - `RbacEndpointPolicyCoverageIntegrationTest` inspects every `HandlerMethod` registered in Spring's `RequestMappingHandlerMapping`, verifies that 100% of `com.rikkei.jobs` controller endpoints have an explicit `RoutePolicy` and matching `@PreAuthorize` annotation on `ROLES` endpoints, verifies all framework/Springdoc/Actuator paths match a `RoutePolicy`, and forbids stale non-infra entries.

### 1.2 Reusable Horizontal Ownership Guard (`OwnershipGuard`) & Rule 14 Compliance

To prevent horizontal Insecure Direct Object Reference (IDOR) probing, Team Lead Decisions `D6` and `D7` mandate that cross-tenant, cross-candidate, or cross-mentor access to another actor's resource ID returns **`404 NOT_FOUND`** with the unified Vietnamese `ErrorResponse {"code":"NOT_FOUND","message":"..."}` body — **byte-identical** to a nonexistent ID — rather than `403 FORBIDDEN`.

- **Class**: `com.rikkei.jobs.common.security.OwnershipGuard` (`public final class`, private constructor, stateless utility methods).
- **Rule 14 Modular Monolith Compliance**:
  - `OwnershipGuard` resides in `com.rikkei.jobs.common.security` and depends **only** on `com.rikkei.jobs.identity.UserPrincipal`, `com.rikkei.jobs.common.exception.ResourceNotFoundException`, and canonical string role constants (`ROLE_CANDIDATE`, `ROLE_HR`, `ROLE_MENTOR`, `ROLE_STAFF`, `ROLE_ADMIN`).
  - It never imports JPA `@Entity` classes, `Role`, or repositories from domain modules (`identity`, `company`, `candidate`, `assessment`, `ai`), avoiding cyclic package dependencies and preserving existing service constructor signatures across unit tests.
- **Why Service-Layer `OwnershipGuard` Instead of SpEL `@PreAuthorize`**:
  - Spring Security `@PreAuthorize` failures throw `AccessDeniedException` (`403 FORBIDDEN`), which leaks resource ownership existence when distinguishing `403` from `404`. Running `OwnershipGuard` inside `@Transactional` service methods ensures failed ownership checks throw `ResourceNotFoundException` (or `EvaluationNotFoundException::new`), returning `404 NOT_FOUND` identical to missing database rows.
- **Provided Helper Methods & Current Call Sites**:
  - `hasRole(...)` / `hasAnyRole(...)`: null-safe uppercase role normalization stripping optional `ROLE_` prefixes.
  - `isSelf(principal, resourceOwnerId)` / `isSelf(callerId, ownerId)`: scalar ID equality check.
  - `requireSelf(callerId, resourceOwnerId, exceptionSupplier)`: throws `ResourceNotFoundException` or domain `NotFoundException` when `callerId != ownerId`. Used by `EvaluationServiceImpl` (`PUT /api/v1/evaluations/{id}`, `POST /api/v1/evaluations/{id}/submit`).
  - `requireSelfOrRoles(callerId, callerRole, targetUserId, selfRoles, bypassRoles, notFoundMessage)`: validates `targetUserId > 0`, checks `bypassRoles` **before** `selfRoles` so an `HR` caller querying `/profiles/{hrOwnId}/skills` or `/evaluations` never bypasses the `is_public = true` domain filter (`404`), and restricts `CANDIDATE` callers strictly to `callerId == targetUserId` (`404` otherwise, even when `is_public = true`). Used by `SkillProfileService` (`GET /api/v1/profiles/{userId}/skills`) and `ProfileEvaluationServiceImpl` (`GET /api/v1/profiles/{userId}/evaluations`).
  - `requireCompanyAccess(principal, targetCompanyId, notFoundMessage)`: rejects `null`/non-positive IDs (`404`), permits `STAFF` to read any positive ID (DB lookup still throws `404` if missing), permits `HR` only when `principal.getCompanyId().equals(targetCompanyId)`, and throws `ResourceNotFoundException("Không tìm thấy doanh nghiệp")` for cross-company or unassigned `HR` (`companyId == null`). Used by `CompanyServiceImpl.getCompanyById` (`GET /api/v1/companies/{id}`).
- **Mandatory Architectural Rule for Future JD Endpoints (`D6` Group B)**:
  - `GET /api/v1/jobs/{jobId}` and `GET /api/v1/target-positions` are `authenticated-any` solely because they expose `APPROVED`, non-expired public JDs (`deadline > now(clock)`) and reference target positions.
  - **Any future endpoint exposing draft JDs (`DRAFT`) or company-scoped JD management/listing MUST enforce `OwnershipGuard` (such as `OwnershipGuard.requireCompanyAccess`) so `HR` can never read or mutate another company's draft JDs.**

### 1.4 Ownership Audit & Contract Changes (`D6` & DN-01 Follow-Up)

1. **ID-Scoped Endpoints Audited**:

### 2.1 Kiến trúc phân quyền khai báo tập trung (`RoutePolicyRegistry` & `SecurityConfig`)

Rikkei Jobs áp dụng nguyên tắc **từ chối mặc định (deny-by-default)** cho toàn bộ HTTP endpoint dựa trên một nguồn chân lý khai báo duy nhất: `com.rikkei.jobs.common.security.RoutePolicyRegistry`.

1. **Một nguồn chân lý duy nhất (`RoutePolicy` + `PolicyAccessType`)**:
   - Mọi endpoint được ánh xạ trong ứng dụng đều được đăng ký một lần trong `RoutePolicyRegistry.POLICIES` dưới dạng bản ghi bất biến `RoutePolicy(method, pattern, accessType, allowedRoles, devOnly, methodScoped, infra, description)`.
   - `PolicyAccessType` định nghĩa ba mức truy cập tường minh:
     - `PUBLIC`: công khai không cần đăng nhập (áp dụng điều kiện profile `devOnly` khi có).
     - `AUTHENTICATED_ANY`: mở cho cả 5 vai trò đã đăng nhập (`CANDIDATE`, `HR`, `MENTOR`, `STAFF`, `ADMIN`).
     - `ROLES`: giới hạn theo tập vai trò cụ thể trong 5 vai trò chuẩn.
   - `SecurityConfig.securityFilterChain(HttpSecurity)` duyệt `RoutePolicyRegistry.policies()` theo đúng thứ tự danh sách, bỏ qua các mục `devOnly` khi profile `dev` không kích hoạt, và kết thúc bằng `.anyRequest().denyAll()`. Mọi đường dẫn chưa khai báo đều trả về `401 UNAUTHORIZED` với người dùng ẩn danh (`CustomAuthenticationEntryPoint`) và `403 FORBIDDEN` với người dùng đã đăng nhập (`CustomAccessDeniedHandler`).
2. **Bất biến thứ tự đường dẫn cụ thể trước tham số hóa**:
   - Các đường dẫn tường minh bắt buộc đứng trước các đường dẫn anh em có tham số trong `RoutePolicyRegistry.POLICIES` để cơ chế khớp đầu tiên (`RequestMatcher`) không bao giờ che khuất chính sách `/me` chặt chẽ hơn:
     - `/api/v1/profiles/me/skills` và `/api/v1/profiles/me/skills/recompute` (chỉ `CANDIDATE`) đứng trước `/api/v1/profiles/{userId}/skills` (`CANDIDATE`, `HR`).
     - `/api/v1/companies/me` (`GET`, `PUT`) và `/api/v1/companies/me/logo` (chỉ `HR`) đứng trước `/api/v1/companies/{id}` (`HR`, `STAFF`).
   - `RoutePolicyRegistryTest` kiểm chứng trực tiếp bất biến thứ tự này.
3. **Phạm vi HTTP Method & Bảo toàn mã lỗi `405 METHOD_NOT_ALLOWED`**:
   - Với các đường dẫn đơn chính sách cần để phương thức HTTP không hỗ trợ đi tới `DispatcherServlet` và trả về `405 METHOD_NOT_ALLOWED` chuẩn hóa, `methodScoped` được đặt là `false` (`/api/v1/auth/forgot-password`, `/api/v1/health`, `/api/v1/companies/me/logo`, `/api/v1/companies/{id}`).
   - Đặc biệt tại `/api/v1/companies/{id}` (quyết định `D6` và quyết định bổ sung của Team Lead), `methodScoped = false` kết hợp `ROLES(HR, STAFF)` bảo đảm:
     - Gọi ẩn danh `PUT /api/v1/companies/{id}` -> `401 UNAUTHORIZED`.
     - `CANDIDATE`, `MENTOR`, `ADMIN` gọi `PUT /api/v1/companies/{id}` -> `403 FORBIDDEN`.
     - `HR` hoặc `STAFF` gọi `PUT /api/v1/companies/{id}` -> đi tới `DispatcherServlet` và trả `405 METHOD_NOT_ALLOWED` đồng nhất cho ID công ty của mình, công ty khác (`2`), và ID không tồn tại (`999999`), không làm thay đổi CSDL (thay thế hành vi `404` trước NT-02 khi chưa có route `/{id}`).
4. **Thứ tự bộ lọc (`MustChangePasswordFilter` so với `@PreAuthorize`)**:
   - Thứ tự xử lý yêu cầu: `JwtAuthFilter` -> `MustChangePasswordFilter` -> `AuthorizationFilter` (`RoutePolicyRegistry`) -> `@EnableMethodSecurity` (`@PreAuthorize`) -> `OwnershipGuard` ở tầng Service.
   - Tài khoản có `must_change_password = true` (như `hr1@rikkeijobs.test`) nhận `403 MUST_CHANGE_PASSWORD` trên mọi endpoint ngoài `ALLOW_LIST` trước khi kiểm tra vai trò hoặc quyền sở hữu. `MustChangePasswordFilter.ALLOW_LIST` chỉ mở cho các route xác thực (`/api/v1/auth/change-password`, `/api/v1/auth/me`, `/api/v1/auth/login`, `/api/v1/auth/sso`, `/api/v1/auth/forgot-password`, `/api/v1/auth/reset-password`), kiểm tra sức khỏe (`/api/v1/health`, `/actuator/health`), OpenAPI/Swagger, `/error`, và `/api/v1/test/**`.
5. **Kiểm thử tự động độ phủ & Tương ứng `@PreAuthorize`**:
   - `RbacEndpointPolicyCoverageIntegrationTest` quét toàn bộ `HandlerMethod` trong `RequestMappingHandlerMapping`, kiểm tra 100% endpoint của `com.rikkei.jobs` có `RoutePolicy` tường minh và `@PreAuthorize` tương ứng cho nhóm `ROLES`, kiểm tra mọi route framework/Springdoc/Actuator đều khớp chính sách, và cấm chính sách phi hạ tầng bị dư thừa.

### 2.2 Tiện ích kiểm tra quyền sở hữu dùng lại (`OwnershipGuard`) & Tuân thủ Rule 14

Để chống lỗ hổng dò ID ngang (IDOR), các quyết định `D6` và `D7` của Team Lead quy định mọi truy cập trái chủ sở hữu (khác doanh nghiệp, khác ứng viên, khác mentor) phải trả về **`404 NOT_FOUND`** với thân JSON tiếng Việt thống nhất `ErrorResponse {"code":"NOT_FOUND","message":"..."}` — **giống hệt từng byte** với ID không tồn tại — thay vì `403 FORBIDDEN`.

- **Lớp tiện ích**: `com.rikkei.jobs.common.security.OwnershipGuard` (`public final class`, private constructor, hàm tĩnh không trạng thái).
- **Tuân thủ ranh giới mô-đun (Rule 14)**:
  - `OwnershipGuard` nằm trong `com.rikkei.jobs.common.security` và **chỉ** phụ thuộc vào `com.rikkei.jobs.identity.UserPrincipal`, `com.rikkei.jobs.common.exception.ResourceNotFoundException`, cùng các hằng số vai trò chuẩn (`ROLE_CANDIDATE`, `ROLE_HR`, `ROLE_MENTOR`, `ROLE_STAFF`, `ROLE_ADMIN`).
  - Hoàn toàn không import `@Entity`, `Role`, hay repository của các mô-đun nghiệp vụ (`identity`, `company`, `candidate`, `assessment`, `ai`), tránh phụ thuộc vòng và giữ nguyên chữ ký constructor của các service cùng unit test hiện có.
- **Lý do đặt ở tầng Service thay vì SpEL `@PreAuthorize`**:
  - Lỗi từ `@PreAuthorize` trả về `403 FORBIDDEN`, vô tình tiết lộ sự tồn tại của tài nguyên khi phân biệt `403` với `404`. Kiểm tra qua `OwnershipGuard` trong service ném `ResourceNotFoundException` (hoặc `EvaluationNotFoundException::new`), trả về `404 NOT_FOUND` đồng nhất với bản ghi không tồn tại.
- **Các phương thức cung cấp & Nơi áp dụng**:
  - `hasRole(...)` / `hasAnyRole(...)`: chuẩn hóa chữ hoa không phân biệt tiền tố `ROLE_` và an toàn với `null`.
  - `isSelf(principal, resourceOwnerId)` / `isSelf(callerId, ownerId)`: so khớp ID vô hướng.
  - `requireSelf(callerId, resourceOwnerId, exceptionSupplier)`: ném ngoại lệ `404` khi `callerId != ownerId`. Dùng tại `EvaluationServiceImpl` (`PUT /api/v1/evaluations/{id}`, `POST /api/v1/evaluations/{id}/submit`).
  - `requireSelfOrRoles(callerId, callerRole, targetUserId, selfRoles, bypassRoles, notFoundMessage)`: kiểm tra `targetUserId > 0`, kiểm tra `bypassRoles` **trước** `selfRoles` để tài khoản `HR` khi gọi `/profiles/{hrOwnId}/skills` hoặc `/evaluations` không vượt qua bước lọc `is_public = true` (`404`), còn `CANDIDATE` chỉ hợp lệ khi `callerId == targetUserId` (người khác trả `404` kể cả khi `is_public = true`). Dùng tại `SkillProfileService` và `ProfileEvaluationServiceImpl`.
  - `requireCompanyAccess(principal, targetCompanyId, notFoundMessage)`: từ chối ID `null`/`<= 0` (`404`), cho phép `STAFF` đọc mọi ID hợp lệ (tìm CSDL nếu thiếu trả `404`), cho phép `HR` chỉ khi `principal.getCompanyId().equals(targetCompanyId)`, và ném `ResourceNotFoundException("Không tìm thấy doanh nghiệp")` cho các trường hợp còn lại (khác công ty hoặc `companyId == null`). Dùng tại `CompanyServiceImpl.getCompanyById` (`GET /api/v1/companies/{id}`).
- **Quy tắc kiến trúc bắt buộc cho API JD tương lai (`D6` Nhóm B)**:
  - `GET /api/v1/jobs/{jobId}` và `GET /api/v1/target-positions` được mở `authenticated-any` chỉ vì cung cấp JD đã duyệt (`APPROVED`) còn hạn (`deadline > now(clock)`) và danh mục vị trí chuẩn.
  - **Mọi endpoint phát triển sau này cho phép xem JD nháp (`DRAFT`) hoặc JD theo từng công ty bắt buộc phải dùng `OwnershipGuard` (như `OwnershipGuard.requireCompanyAccess`) để `HR` không thể đọc hoặc sửa JD nháp của doanh nghiệp khác.**

### 2.4 Tổng hợp kiểm toán quyền sở hữu & Thay đổi hợp đồng (`D6` & DN-01)

1. **Các endpoint nhận tham số ID đã kiểm toán**:
   - `GET /api/v1/companies/{id}` (mới ở NT-02 `D6`): `OwnershipGuard.requireCompanyAccess` cho phép `HR` đọc đúng công ty mình (`404` giống hệt ID thiếu nếu lệch công ty hoặc chưa gán) và `STAFF` đọc mọi công ty (`404` nếu thiếu).
   - `GET /api/v1/profiles/{userId}/skills` (`D6` Nhóm C): khóa chặt qua `OwnershipGuard.requireSelfOrRoles` giống `/evaluations` (`CANDIDATE` xem ứng viên khác -> `404` kể cả khi `is_public = true`; `HR` chỉ xem hồ sơ công khai; `MENTOR`/`STAFF`/`ADMIN` -> `403`). Đã cập nhật `SkillProfileIntegrationTest.java`, `e2e/tier2-boundaries/test_auth_boundaries.test.mjs` (`TC-T2-SKILL-02`), và `docs/hs-01-skill-profile.md`.
   - `GET /api/v1/profiles/{userId}/evaluations`: chuẩn hóa qua `OwnershipGuard.requireSelfOrRoles` (`CANDIDATE` chỉ chính mình; `HR` chỉ `is_public = true`; vai trò khác `403`).
   - `PUT /api/v1/evaluations/{id}` và `POST /api/v1/evaluations/{id}/submit`: chuẩn hóa qua `OwnershipGuard.requireSelf(..., EvaluationNotFoundException::new)`.
   - `POST /api/v1/staff/companies/{id}/hr-accounts`: thao tác quản trị toàn cục của `STAFF` (`404` nếu doanh nghiệp `{id}` không tồn tại).
   - `GET /api/v1/jobs/{jobId}` (`D6` Nhóm B): `authenticated-any` cho JD `APPROVED` còn hạn (`404` với nháp/hết hạn/không tồn tại).
2. **Các endpoint tự phục vụ `/me` đã kiểm toán**:
   - `GET/POST /api/v1/profiles/me/skills*`, `PUT/GET /api/v1/me/target`, `GET /api/v1/me/gap-analysis` (`D6` Nhóm A): khóa từ `anyRequest().authenticated()` về chỉ `CANDIDATE`.
   - `GET /api/v1/me/job-recommendations`: chỉ `CANDIDATE` (`principal.getId()`, bỏ qua mọi tham số `userId`).
   - `GET/PUT /api/v1/companies/me` và `POST /api/v1/companies/me/logo`: chỉ `HR` (`principal.getCompanyId()`, bỏ qua `id` từ body).
   - `GET /api/v1/auth/me` và `POST /api/v1/auth/change-password`: `AUTHENTICATED_ANY` (`principal.getId()`, nằm trong `ALLOW_LIST`).
3. **Thay đổi hợp đồng `PUT /api/v1/companies/{id}` (`404` -> `405 METHOD_NOT_ALLOWED`)**:
   - Trước NT-02 (`DN-01`), `/api/v1/companies/{id}` chưa có route nên `PUT /api/v1/companies/{id}` trả `404 NOT_FOUND`.
   - Sau khi NT-02 (`D6`) ánh xạ `GET /api/v1/companies/{id}` với `RoutePolicy.methodScoped = false`, `PUT /api/v1/companies/{id}` trả về `405 METHOD_NOT_ALLOWED` đồng nhất cho `HR` và `STAFF` trên cả ID công ty mình, công ty khác, và ID không tồn tại (CSDL không đổi), `403 FORBIDDEN` cho `CANDIDATE`/`MENTOR`/`ADMIN`, và `401 UNAUTHORIZED` cho người gọi ẩn danh.
